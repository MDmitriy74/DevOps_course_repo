# Домашняя подготовка: GitLab, GitLab Runner и Kubernetes

Подготовьте стенд **до занятия по GitLab CI/CD**. На занятии будем писать `.gitlab-ci.yml`, собирать Dockerfile, отправлять образ в локальный Registry и развёртывать приложение в Kubernetes. Здесь мы создаём инфраструктуру и проверяем соединения; pipeline пока не пишем. Стандартное имя файла GitLab — `.gitlab-ci.yml`.

Все компоненты работают на компьютере студента. GitLab и Runner запускаем отдельными контейнерами **вручную, без Docker Compose**: создаём сеть, тома, задаём параметры `docker run`. Kubernetes — существующий кластер `hosting-lab` из предыдущих занятий. Пересоздавать исправный кластер не нужно.

Оставьте на подготовку несколько часов: образы большие, первый запуск GitLab включает настройку базы данных. Нужен интернет, в том числе доступ к Docker Hub, registry.gitlab.com и registry.k8s.io.

## 1. Инструменты и ресурсы

| Система | Что используем | Где выполняем команды |
|---|---|---|
| Windows x64 | Docker Desktop: Linux containers, WSL2 backend, интеграция с Ubuntu; kind, kubectl и Git внутри Ubuntu | Bash в Ubuntu WSL2 |
| macOS Intel | Docker Desktop, kind, kubectl, Git | Bash в Terminal |
| macOS Apple Silicon | Docker Desktop для Apple Silicon, kind, kubectl, Git | Bash в Terminal |
| Linux x64 / ARM64 | Docker Engine, kind, kubectl, Git | Bash |

Установка инструментов описана в [подготовке к Kubernetes](../README.md#1-установить-инструменты). В Windows не устанавливайте второй Docker Engine внутри Ubuntu. Рабочие файлы храните в `~/hosting-lab` в файловой системе WSL. Данные GitLab сохраняем в Docker volumes, чтобы не зависеть от прав на каталог Windows, macOS или синхронизируемой папки.

**Ресурсов прежнего Kubernetes-стенда теперь может не хватить.** Планируйте компьютер с 16 ГБ RAM или больше; для Docker Desktop/WSL ориентир — 4 CPU и 10–12 ГБ RAM на весь стенд. Это ориентир для пробного прогона, а не гарантия: сборка приложения требует дополнительной памяти. Оставьте примерно 50 ГБ свободного диска. На компьютере с 8 ГБ RAM заранее сообщите преподавателю: одновременная работа GitLab, Kubernetes и сборки на нём не гарантируется. Не останавливайте Kubernetes ради формального выполнения проверки GitLab: на занятии нужны оба.

В Docker Desktop на macOS проверьте лимиты в Settings → Resources. В Windows ресурсы WSL2 задаются в настройках WSL; изменение `.wslconfig` требует перезапуска WSL. На Linux контейнеры используют ресурсы хоста.

Проверки:

```bash
docker version
docker info
kind version
kubectl version --client
git --version
docker run --rm hello-world
```

У `docker version` должны быть Client и Server. Все команды выполняйте одним пользователем. Инструкция рассчитана на локальный Docker Engine / Docker Desktop с сокетом `/var/run/docker.sock`; удалённый Docker context, rootless Docker и Podman требуют другой настройки socket и здесь не используются. Не исправляйте ошибки доступа командой `chmod 666` для сокета.

GitLab не заявляет официальную поддержку Docker for Windows; WSL2 с Linux-контейнерами — наш учебный вариант, который нужно проверить на своей машине до занятия. Если он не запускается, сохраните диагностику из раздела 12 и сообщите преподавателю.

## 2. Проверить Kubernetes и Registry

Этот раздел включает подготовку из первой практики. Откройте терминал **в корне материалов**, где лежат `local/` и основной `README.md`.

Сначала определите, существует ли кластер:

```bash
kind get clusters
docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

Если `hosting-lab` и `hosting-lab-registry` уже есть, при необходимости запустите остановленные контейнеры:

```bash
docker start hosting-lab-registry hosting-lab-control-plane
```

Если стенда ещё нет, создайте его **один раз**:

```bash
bash local/setup.sh
```

Скрипт создаёт отдельный Registry на `127.0.0.1:5001` и один узел Kubernetes. Он останавливается при уже существующих ресурсах. При частично созданном стенде сначала разберите ошибку по [основному README](../README.md), не удаляйте исправный кластер автоматически.

```bash
kubectl --context kind-hosting-lab get nodes -o wide
kubectl --context kind-hosting-lab get pods -A
```

Ожидаются узел `hosting-lab-control-plane` в состоянии `Ready` и работающие системные Pod.

Если build → push → запуск после предыдущей практики ещё не проверяли, выполните [раздел 3 основного README](../README.md#3-проверить-build--push--запуск-в-kubernetes). Там собирается `local/web`, образ отправляется в `localhost:5001`, затем запускается Pod и проверяется через `localhost:8081`. После проверки удалите только namespace `hosting-check`, как указано там. На Apple Silicon сборка и Kubernetes остаются в родной архитектуре: не добавляйте им `--platform linux/amd64`.

Порты нового стенда не пересекаются с прежними:

| Адрес компьютера | Назначение |
|---|---|
| `127.0.0.1:5001` | Существующий Registry |
| `127.0.0.1:8080`, `127.0.0.1:8443` | Существующий Ingress Kubernetes |
| `127.0.0.1:8929` | Новый GitLab по HTTP |

## 3. Как соединяются компоненты

```text
Компьютер студента
  браузер → http://localhost:8929 → контейнер GitLab
  Docker daemon
    сеть gitlab-lab
      fiit-gitlab          (сетевое имя gitlab, порт 8929)
      fiit-runner          (постоянный процесс GitLab Runner)
      контейнеры заданий   (создаёт Runner на время job)
      hosting-lab-control-plane (дополнительно подключим к этой сети)
    сеть kind
      hosting-lab-control-plane → containerd → Pod приложения
      hosting-lab-registry
```

Runner опрашивает GitLab и создаёт контейнеры заданий через socket Docker. В job будет Docker CLI, который через тот же socket обращается к **тому же Docker daemon компьютера**. Образы и создаваемые контейнеры будут видны в обычных `docker images` и `docker ps`.

`localhost` внутри контейнера означает этот контейнер. Поэтому используем разные адреса:

| Откуда                           | Куда обращаемся                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------- |
| Браузер, Git на компьютере       | `http://localhost:8929`                                                         |
| Runner и контейнеры заданий      | `http://gitlab:8929`                                                            |
| kubectl на компьютере            | Адрес из обычного kubeconfig kind                                               |
| kubectl в контейнере задания     | `https://hosting-lab-control-plane:6443` из внутреннего kubeconfig              |
| `docker push localhost:5001/...` | Docker daemon компьютера отправляет образ в существующий Registry               |
| containerd внутри узла           | Скачивает `localhost:5001/...` через настроенный в первой практике `hosts.toml` |

Последняя строка важна: Docker компьютера и containerd Kubernetes имеют отдельные хранилища. Одного `docker build` для запуска нового образа в Pod недостаточно.

## 4. Скачать образы

На свежем учебном стенде используем официальные образы GitLab CE и Runner. Здесь `latest` означает актуальный образ **на момент подготовки**. После скачивания сохраним локальные теги и запишем версии: повторно скачивать `latest` перед занятием не нужно. Если преподаватель выдал конкретные согласованные версии, используйте их вместо `latest`.

```bash
docker pull gitlab/gitlab-ce:latest
docker pull gitlab/gitlab-runner:latest
docker pull docker:cli
docker pull alpine:3
```

**Apple Silicon / Linux ARM64:** сначала пробуем скачать GitLab без смены платформы. Если именно GitLab CE сообщает `no matching manifest for linux/arm64`, скачайте его amd64-вариант:

```bash
docker pull --platform linux/amd64 gitlab/gitlab-ce:latest
```

В этом случае ниже в команду запуска **только GitLab** добавьте `--platform linux/amd64`. На Apple Silicon нужна работающая эмуляция amd64 в Docker Desktop; если выбран режим с Rosetta, включите соответствующую настройку Docker Desktop. Эмуляция замедляет запуск и повышает требования к ресурсам. На Linux ARM64 автоматическая эмуляция может отсутствовать: если нативного образа нет и amd64 не запускается, сообщите преподавателю до занятия. Не заменяйте официальный образ случайной ARM-сборкой.

Runner, образы заданий и kind запускаем в родной архитектуре. Наличие ARM64-пакета GitLab само по себе не доказывает наличие ARM64-варианта выбранного Docker-тега.

После успешного скачивания создайте локальные теги:

```bash
docker tag gitlab/gitlab-ce:latest fiit/gitlab:lab
docker tag gitlab/gitlab-runner:latest fiit/runner:lab
docker tag docker:cli fiit/docker-cli:lab
docker image inspect fiit/gitlab:lab fiit/runner:lab fiit/docker-cli:lab \
  --format '{{.RepoTags}} {{.Os}}/{{.Architecture}} {{.Id}}'
```

Сохраните вывод в отчёте. Локальные теги фиксируют скачанные образы на этом компьютере, но у разных студентов версии могут отличаться. Выбор единых точных тегов для группы преподаватель делает после пробного запуска. Не обновляйте GitLab с существующими данными простым повтором этих команд: обновление требует отдельной процедуры.

## 5. Создать сеть и тома

```bash
docker network create gitlab-lab
docker volume create fiit-gitlab-config
docker volume create fiit-gitlab-logs
docker volume create fiit-gitlab-data
docker volume create fiit-runner-config
```

Сеть даёт контейнерам DNS-имена и возможность обращаться друг к другу. Тома сохраняют конфигурацию, базу, репозитории и регистрацию Runner при удалении контейнера. Удаление тома с данными уничтожает данные.

```bash
docker network inspect gitlab-lab
docker volume inspect fiit-gitlab-config fiit-gitlab-logs fiit-gitlab-data fiit-runner-config
```

Если сеть уже существует после предыдущей попытки, проверьте её и продолжайте; создавать вторую с тем же именем не нужно. Контейнер с занятым именем тоже сначала проверьте через `docker ps -a`.

## 6. Запустить GitLab

```bash
docker run -d \
  --name fiit-gitlab \
  --hostname gitlab \
  --network gitlab-lab \
  --network-alias gitlab \
  --restart unless-stopped \
  --publish 127.0.0.1:8929:8929 \
  --shm-size 256m \
  --volume fiit-gitlab-config:/etc/gitlab \
  --volume fiit-gitlab-logs:/var/log/gitlab \
  --volume fiit-gitlab-data:/var/opt/gitlab \
  --env GITLAB_OMNIBUS_CONFIG="external_url 'http://localhost:8929'; nginx['listen_port'] = 8929; letsencrypt['enable'] = false; puma['worker_processes'] = 0; sidekiq['concurrency'] = 10; prometheus_monitoring['enable'] = false; gitlab_kas['enable'] = false;" \
  fiit/gitlab:lab
```

Если на ARM скачивали amd64-образ, добавьте `--platform linux/amd64` после `docker run -d`.

Что задают параметры:

- `--network-alias gitlab` — имя GitLab в Docker-сети;
- `--publish 127.0.0.1:8929:8929` — HTTP доступен только с компьютера студента;
- `external_url` — адрес, который GitLab показывает пользователю; `nginx['listen_port']` — порт внутри контейнера;
- три `--volume` — постоянные данные;
- `--shm-size` — общая память контейнера для внутренних процессов;
- параметры Puma, Sidekiq и отключение мониторинга уменьшают нагрузку для одного пользователя;
- `gitlab_kas` выключен, поскольку будем подключаться к локальному Kubernetes напрямую через kubeconfig.

HTTPS, SSH, SMTP и встроенный Container Registry GitLab в этой подготовке не настраиваем. Для образов уже есть `hosting-lab-registry`, для Git используем HTTP. Это локальная учебная установка; официальный сценарий установки GitLab предполагает доступное имя хоста, а здесь внутренний адрес для Runner зададим отдельно.

Посмотрите запуск:

```bash
docker logs --tail 80 -f fiit-gitlab
```

Первый запуск может занять десятки минут, особенно при эмуляции. Ctrl+C прекращает просмотр логов, контейнер продолжает работать. Статус `Up` сам по себе не означает готовность GitLab.

```bash
docker exec fiit-gitlab gitlab-ctl status
curl --fail --show-error http://localhost:8929/-/readiness
```

Дождитесь успешного HTTP-ответа readiness и страницы входа <http://localhost:8929>. Если `curl` ещё возвращает ошибку, изучите логи, дождитесь окончания первичной настройки и повторите. Если в WSL запрос успешен, а браузер Windows не открывает страницу, проверьте localhost forwarding WSL/Docker Desktop, VPN и локальный firewall.

## 7. Войти и создать учебный проект

Получите временный пароль администратора:

```bash
docker exec fiit-gitlab cat /etc/gitlab/initial_root_password
```

Войдите как `root`, смените пароль и сохраните его в менеджере паролей. Файл временного пароля может быть удалён спустя 24 часа при последующей перенастройке/перезапуске. Если он уже отсутствует, сбросьте пароль интерактивно:

```bash
docker exec -it fiit-gitlab gitlab-rake 'gitlab:password:reset[root]'
```

Для единственного локального учебного проекта можно продолжить под `root`. В Admin → Settings → General → Sign-up restrictions отключите публичную регистрацию пользователей. Почтовый сервер для этих действий не нужен.

Создайте **Create blank project**:

- Project name / slug: `hosting-ci`;
- Visibility: Private;
- Initialize repository with a README: включено;
- шаблон CI/CD / Auto DevOps не включайте.

В результате есть проект `root/hosting-ci`, в нём README и ветка `main`. Файл `.gitlab-ci.yml` добавим на занятии. Если Auto DevOps включён на уровне инстанса, выключите его для проекта в Settings → CI/CD → Auto DevOps, чтобы не запускать автоматический pipeline.

## 8. Запустить и зарегистрировать Runner

Регистрация входит в домашнюю подготовку: она короткая и позволяет обнаружить проблемы сети до занятия.

### 8.1. Запустить постоянный контейнер

```bash
docker run -d \
  --name fiit-runner \
  --network gitlab-lab \
  --restart unless-stopped \
  --volume fiit-runner-config:/etc/gitlab-runner \
  --volume /var/run/docker.sock:/var/run/docker.sock \
  fiit/runner:lab
```

Этот socket нужен **процессу Runner**, чтобы создавать контейнеры заданий. Для команд `docker build` внутри job отдельно добавим такой же mount в настройки Docker executor при регистрации.

Доступ к socket позволяет job управлять Docker компьютера, в том числе контейнерами GitLab и Kubernetes. Используйте этот Runner только для собственного учебного проекта и доверенного кода; не подключайте его к общедоступным проектам.

### 8.2. Создать Runner в интерфейсе GitLab

В проекте откройте Settings → CI/CD → Runners → Create project runner (в некоторых версиях кнопка называется New project runner).

- Система: Linux, поскольку Runner работает в Linux-контейнере даже на Windows/macOS.
- Tag: `local-docker`.
- Run untagged jobs: выключено.
- Description: `student-local-docker`.
- Protected: выключено для этого локального учебного проекта, чтобы на занятии выполнять задания из обычных веток.

Создайте Runner и скопируйте **runner authentication token**, начинающийся с `glrt-`. Он показывается ограниченное время. Не используйте устаревший registration token и параметр `--registration-token`. Теги и разрешение на untagged jobs задаются в UI, а не флагами регистрации с authentication token.

### 8.3. Зарегистрировать Docker executor

Запустите команду в Bash. Она запросит токен без отображения ввода; после вставки нажмите Enter. В историю команд значение токена не записывается. Выполните блок один раз, после успешной регистрации повторять его не нужно.

```bash
read -r -s -p 'Runner token (glrt-...): ' FIIT_RUNNER_TOKEN
echo
docker exec fiit-runner gitlab-runner register \
  --non-interactive \
  --url 'http://gitlab:8929' \
  --clone-url 'http://gitlab:8929' \
  --token "glrt-e0b5ge3TfEiLHeup79Z7MG86MQpwOjEKdDozCnU6MQ8.01.170yz0atk" \
  --executor docker \
  --description student-local-docker \
  --docker-image fiit/docker-cli:lab \
  --docker-pull-policy if-not-present \
  --docker-network-mode gitlab-lab \
  --docker-volumes /var/run/docker.sock:/var/run/docker.sock \
  --docker-volumes /cache
unset FIIT_RUNNER_TOKEN
docker restart fiit-runner
```

Ожидается сообщение об успешной регистрации. Не копируйте предложенный UI адрес `localhost` в эту команду: она выполняется внутри Runner.

`--url` задаёт внутренний адрес для связи Runner с GitLab, в том числе обмена заданиями и артефактами. `--clone-url` заменяет внешний адрес при checkout репозитория. `--docker-network-mode` подключает **контейнеры заданий и helper-контейнеры** к нашей сети: подключения только самого Runner недостаточно. `if-not-present` позволяет использовать предварительно скачанный локальный образ CLI. `privileged` не включаем; Docker-in-Docker и сервис `docker:dind` здесь не нужны.

Проверить регистрацию:

```bash
docker exec fiit-runner gitlab-runner verify
docker logs --tail 50 fiit-runner
```

В GitLab Runner должен стать Online и отображаться у проекта с тегом `local-docker`. Это подтверждает связь Runner с GitLab, но ещё не доказывает выполнение CI job. Проверку checkout и артефактов сделаем первым pipeline на занятии.

В `fiit-runner-config` должен получиться конфиг примерно такой структуры; **это пример для сравнения, не замена файла с реальным токеном**:

```toml
concurrent = 1

[[runners]]
  name = "student-local-docker"
  url = "http://gitlab:8929"
  clone_url = "http://gitlab:8929"
  token = "glrt-СКРЫТО"
  executor = "docker"
  [runners.docker]
    image = "fiit/docker-cli:lab"
    privileged = false
    network_mode = "gitlab-lab"
    pull_policy = ["if-not-present"]
    volumes = ["/var/run/docker.sock:/var/run/docker.sock", "/cache"]
```

Конфиг содержит секрет: не прикладывайте полный файл к отчёту и не коммитьте его.

## 9. Проверить Docker из будущего окружения задания

Пока запускаем диагностический контейнер вручную. По сети, socket и образу он соответствует будущему job, но не проверяет планирование задания самим Runner.

```bash
docker run --rm \
  --network gitlab-lab \
  --volume /var/run/docker.sock:/var/run/docker.sock \
  fiit/docker-cli:lab sh -ec '
    docker version
    docker ps --format "table {{.Names}}\t{{.Status}}"
    wget -qO- http://gitlab:8929/-/readiness
  '
```

Ожидаются Client и Server Docker, контейнеры стенда в списке и успешная readiness GitLab. Так проверяем сразу DNS, HTTP и доступ к Docker daemon из контейнера. CLI устанавливать внутрь постоянного Runner не нужно.

Для сборки на занятии используем `docker build ... .`: CLI передаёт build context Docker daemon. Но при `docker run -v /путь:/путь` исходный путь ищется **на стороне daemon**, а не внутри job. Не переносите произвольные bind mounts из терминала в CI без проверки.

## 10. Подготовить доступ к Kubernetes из контейнеров

Обычный kubeconfig на компьютере содержит `127.0.0.1` и случайный опубликованный порт API. В job этот адрес не указывает на Kubernetes. Подключим существующий узел к нашей сети и сохраним **отдельный внутренний kubeconfig**, не меняя основной.

```bash
docker network connect gitlab-lab hosting-lab-control-plane
```

Если узел уже подключён, Docker сообщит об этом; повторять подключение не требуется. Основную сеть `kind` у узла не отключайте.

```bash
mkdir -p "$HOME/.config/fiit-gitlab"
chmod 700 "$HOME/.config/fiit-gitlab"
(umask 077; kind get kubeconfig --name hosting-lab --internal \
  > "$HOME/.config/fiit-gitlab/kubeconfig")
kubectl --kubeconfig "$HOME/.config/fiit-gitlab/kubeconfig" \
  config view --minify -o jsonpath='{.clusters[0].cluster.server}'
echo
```

Ожидается `https://hosting-lab-control-plane:6443`. Этот внутренний адрес предназначен для контейнеров нашей Docker-сети; с компьютера продолжайте использовать обычный контекст `kind-hosting-lab`.

Проверим доступ официальным kubectl-контейнером той же версии, что сервер Kubernetes. Файл передаём через stdin, чтобы не зависеть от host bind mounts в WSL/macOS:

```bash
FIIT_KUBE_VERSION=$(kubectl --context kind-hosting-lab version -o jsonpath='{.serverVersion.gitVersion}')
docker pull "registry.k8s.io/kubectl:$FIIT_KUBE_VERSION"
docker run --rm -i \
  --network gitlab-lab \
  "registry.k8s.io/kubectl:$FIIT_KUBE_VERSION" \
  --kubeconfig /dev/stdin get nodes \
  < "$HOME/.config/fiit-gitlab/kubeconfig"
```

Ожидается тот же узел `Ready`. Эта проверка использует аутентификацию и проверку TLS; `--insecure-skip-tls-verify` не нужен.

Внутренний kubeconfig содержит административный клиентский сертификат **только этого одноразового локального кластера**. Не отправляйте его в отчёт или Git. На занятии сохраним его в приватном проекте как CI/CD variable типа File с именем `KUBECONFIG`. Для deploy job подготовим образ с kubectl и shell, совместимый с Docker executor: диагностический kubectl-образ из команды выше не следует автоматически использовать как образ job. Не используйте здесь kubeconfig рабочего или общего кластера. После пересоздания kind заново подключите узел к сети и экспортируйте kubeconfig: сертификаты изменятся.

## 11. Что должно быть готово к занятию

Создайте `REPORT.md` с краткими результатами и текстовым выводом проверок:

1. ОС, архитектура, версии Docker/kind/kubectl и доступные Docker CPU/RAM.
2. `docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'`: GitLab, Runner, узел kind и Registry работают одновременно.
3. Версии GitLab и Runner, ID и архитектуры скачанных образов из раздела 4.
4. Успешный `curl http://localhost:8929/-/readiness` и путь проекта `root/hosting-ci`.
5. Runner Online, тег `local-docker` и вывод `gitlab-runner verify` без токенов.
6. Результат раздела 9: Docker Server доступен из диагностического контейнера, GitLab отвечает по внутреннему имени.
7. `kubectl --context kind-hosting-lab get nodes -o wide` и результат `get nodes` из контейнера в разделе 10.
8. Подтверждение успешной проверки build → push → Pod из прежней подготовки, либо ошибка, на которой остановились.

Версии можно получить так:

```bash
docker exec fiit-gitlab cat /opt/gitlab/embedded/service/gitlab-rails/VERSION
docker exec fiit-runner gitlab-runner --version
```

Перед отправкой просмотрите вывод: скройте пароли, токены и содержимое kubeconfig. Скриншот интерфейса можно приложить дополнительно к текстовому отчёту.

Критерий готовности: открывается GitLab, создан проект, Runner Online, из контейнера доступны Docker daemon и Kubernetes, кластер и Registry работают одновременно с GitLab. **Успешный pipeline в домашней подготовке не требуется.** Если регистрацию Runner не удалось закончить, принесите точную ошибку и диагностику; исправим подключение перед первым job, но основная цель — зарегистрировать его дома.

## 12. Диагностика

| Симптом | Что проверить |
|---|---|
| `port is already allocated` | Кто занял 8929. Порты 8080/8443 оставьте Kubernetes. При смене 8929 измените публикацию, `external_url`, `listen_port` и оба URL Runner согласованно |
| GitLab отдаёт 502 / readiness не успешна | Идёт ли первоначальная настройка, логи и `gitlab-ctl status`; свободные RAM/диск |
| GitLab завершился / постоянно перезапускается | `docker inspect fiit-gitlab --format '{{.State.Status}} OOM={{.State.OOMKilled}} Exit={{.State.ExitCode}}'`, логи; при нехватке RAM увеличьте ресурсы всей среды Docker/WSL |
| `exec format error` / `no matching manifest` | Архитектура конкретного образа; ARM-ветка раздела 4. Не переключайте весь стенд на amd64 |
| Runner Offline / connection refused | Готовность GitLab, сеть `gitlab-lab`, URL `http://gitlab:8929`, логи Runner |
| В CI checkout пытается идти на localhost | Наличие `clone_url = "http://gitlab:8929"`, сеть заданий, а не только сеть постоянного Runner |
| `docker: not found` | Job должен использовать образ с Docker CLI, например подготовленный `fiit/docker-cli:lab` |
| CLI не видит Docker Server | Socket нужен в mounts Runner и в `runners.docker.volumes`; `DOCKER_HOST=tcp://docker:2375` из DinD-примера здесь не нужен |
| Job остаётся Pending | Тег job должен быть `local-docker`; Runner Online, не paused; правила Protected соответствуют ветке |
| В job недоступен API GitLab через `$CI_API_V4_URL` | GitLab формирует переменную из внешнего `localhost`. Для обращений из контейнера используйте `http://gitlab:8929/api/v4`; `clone_url` не переписывает произвольные URL и LFS |
| Kubernetes доступен на компьютере, но не из контейнера | Узел подключён к `gitlab-lab`, выбран внутренний kubeconfig; после пересоздания кластера экспорт повторён |
| Kubernetes не скачивает образ | Успешный push, точный тег, `hosts.toml` и containerdConfigPatches из прежней практики; Docker image store отличается от containerd |

Безопасная диагностика, не печатающая конфиг Runner или kubeconfig:

```bash
docker logs --tail 100 fiit-gitlab
docker logs --tail 100 fiit-runner
docker exec fiit-gitlab gitlab-ctl status
docker network inspect gitlab-lab --format '{{range .Containers}}{{println .Name}}{{end}}'
docker stats --no-stream
kubectl --context kind-hosting-lab get nodes
kubectl --context kind-hosting-lab get pods -A
```

Перед публикацией логов проверьте, нет ли в них чувствительных данных. На Linux с SELinux ошибка socket-доступа может требовать настройки политики; не выключайте SELinux целиком — сохраните ошибку для разбора.

## 13. Остановить и снова включить стенд

После подготовки можно остановить GitLab и Runner, чтобы освободить ресурсы:

```bash
docker stop fiit-runner fiit-gitlab
```

Перед занятием запустите Docker, контейнеры и повторите проверки. Явно остановленный контейнер с `unless-stopped` сам не запустится:

```bash
docker start hosting-lab-registry hosting-lab-control-plane fiit-gitlab fiit-runner
curl --fail --show-error http://localhost:8929/-/readiness
docker exec fiit-runner gitlab-runner verify
kubectl --context kind-hosting-lab get nodes
```

После старта снова дождитесь готовности GitLab. Регистрация Runner сохраняется в томе, выполнять её заново не нужно.

## 14. Удаление после завершения курса

Удаление контейнеров сохраняет именованные тома:

```bash
docker stop fiit-runner fiit-gitlab
docker rm fiit-runner fiit-gitlab
docker network disconnect gitlab-lab hosting-lab-control-plane
docker network rm gitlab-lab
```

Следующий блок **необратимо удаляет GitLab с проектами и регистрацию Runner**. Выполняйте его только после завершения всех занятий и сохранения нужных материалов:

```bash
docker volume rm fiit-runner-config fiit-gitlab-config fiit-gitlab-logs fiit-gitlab-data
rm "$HOME/.config/fiit-gitlab/kubeconfig"
```
